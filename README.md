# Encrypz

A Google Drive vault with browser-side encryption. No application database is required.

1. Sign in with Google and allow Encrypz to use its private Drive app storage.
2. Set a master password. Your browser generates a random AES-256 vault key and encrypts it with a password-derived key.
3. On any device, sign in to the same Google account and enter the same master password to unlock your files.

The password and decrypted vault key never reach the API and are never written to browser storage. The key is a non-exportable Web Crypto key held in memory. Reloading the page locks the vault. File contents, filenames, thumbnails, and folder names are encrypted with AES-GCM. File sizes, dates, record IDs, and folder relationships remain metadata visible to the API.

## Local development

Prerequisites: .NET 8 SDK and Node.js 24.

Copy `.env.example` to `.env` and set `GoogleDrive__ClientId` and `GoogleDrive__ClientSecret`. Enable the Google Drive API and configure a Google OAuth web client. No MongoDB URI is needed. Configure the callback `http://localhost:5207/api/Auth/google-callback`. This is the redirect URI generated by the current local API and Vite proxy configuration.

```bash
npm ci --prefix Encrypz.UI
npm run dev --prefix Encrypz.UI
```

In another terminal:

```bash
dotnet run --project Encrypz.API --launch-profile http
```

Open http://localhost:5173. Use the configured frontend hostname consistently; browser write requests require its exact origin.

```bash
dotnet test Encrypz.Tests/Encrypz.Tests.csproj
npm test --prefix Encrypz.UI
npm run build --prefix Encrypz.UI
```

## Storage and sessions

Drive's hidden `appDataFolder` holds the encrypted vault configuration, encrypted file payloads, and separate file/folder records. The application requests `drive.appdata`; `drive.file` is also requested to read original Encrypz files during migration. See [Google's application data documentation](https://developers.google.com/workspace/drive/api/guides/appdata).

PBKDF2-HMAC-SHA-256 with a random 32-byte salt and 600,000 iterations derives the AES-GCM wrapping key. The encrypted random vault key is authenticated against the current Google account's stable ID. A wrong password fails locally when that key cannot be decrypted. Google authentication authorizes access to encrypted records; the server does not verify the master password or claim that an encrypted record request proves knowledge of it.

Each Google account has an independent vault. Account linking across Google accounts is no longer supported. OAuth tokens are stored only in temporary server memory behind an opaque HttpOnly session cookie; sessions expire after at most 50 minutes or on server restart. Deploy one API instance: multiple instances would require shared session storage or a different session design. Nothing needed to decrypt a vault depends on those temporary sessions.

Records are separate Drive documents, so independent uploads do not overwrite a shared manifest. Concurrent trash/restore operations on the same item use the last completed write. A permanently deleted record is not recreated by a late update. Setup should finish on one device before opening another: Drive does not enforce unique names, so duplicate configuration records fail closed and require manual recovery. Drive errors never initialize a replacement vault.

The recycle bin retains files until explicitly permanently deleted. There is no background expiry job. Upload requests are limited to 100 MB including base64/JSON overhead. Failed metadata creation may leave an orphaned encrypted blob in app storage; it is retained for recovery. This version lists record documents individually and is intended for modest personal vaults.

## Backup and recovery

Download your encrypted configuration backup from **Profile → Back up vault configuration**. If the configuration alone is lost, choose that backup on the login screen and enter its original master password to restore it. An existing configuration cannot be overwritten. A configuration backup does **not** contain the files and does not recover a forgotten password. Deleting Encrypz's Drive application data can permanently delete the entire vault. Keep independent backups of important files.

## Importing an existing MongoDB vault

Existing database records are not automatically migrated or deleted. Back up the old database before switching deployments. The new application does not connect to it. The archived SQL migrations remain reference material only.

Export `Users`, `EncryptedFiles`, and `Folders` using `mongoexport --jsonArray` (or equivalent Extended JSON exports), then prepare a token-free metadata bundle locally:

```bash
python3 scripts/prepare-legacy-import.py --users Users.json --files EncryptedFiles.json --folders Folders.json --user-id YOUR-USER-UUID --output legacy-vault.json
```

Create/unlock the new Drive vault, then select **Profile → Import an older vault**. Choose the bundle and enter the original master password. The browser downloads original encrypted files, verifies/decrypts them locally, and re-encrypts copies with the new vault key. Folder structure and recycle-bin flags are preserved; old thumbnails are not copied. Original Drive files and exports remain unchanged. Sign in with the Google account containing those original files. Multi-account legacy vaults need a separate bundle/import for the files belonging to each account; this version does not combine Google accounts into one vault.

Keep the import tab open. Successful imports are remembered for retries within that tab; restarting an import after reloading can create duplicates. Recovering old ciphertext without its metadata and original password is not supported.
